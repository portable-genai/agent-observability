- **Note:** Hrz5 is a **horizontal control-plane service** (the platform's observability / WORM-audit / FinOps
  system of record), not an agent. It exposes ONE persistence port (`AuditSinkPort`) over three profiles
  (`gcp | local | onprem`); it does no grounded LLM reasoning, has no UI, and is *consumed by* the other
  systems (Rsk1 et al.) rather than consuming them. Applicability is judged on that basis: `[agentic]` and
  `[ui]` checks that presuppose a model runtime or a browser surface are marked **N-A by design** with a
  reason (not FAIL); the audit/WORM (C9) and inbound S2S (C7) checks (where Hrz5 is the reference owner)
  are audited closely. Each check was re-run against the current tree; the offline gate (ruff + format +
  mypy + 87 tests + eval + demo + portability proof) was executed green with only `[dev]` installed
  (no Google Cloud SDK), plus `terraform fmt -check` and `terraform validate` with no cloud
  credentials.

Applicability: no `ui/` (so `[ui]` checks are N-A) and ships Terraform (`infra/terraform/`, so `[infra]`
applies). **Load-bearing** checks (a FAIL breaks a shared catalog guarantee) are A1-A6, C1-C5, D1-D3 and E1:

SQLite triggers refuse UPDATE and refuse DELETE outside a recorded retention prune; every record is hash-chained over canonical JSON; the external anchor (`OBSERVABILITY_LOCAL_ANCHOR`, defaulted beside the store and documented as needing a different volume to mean anything) carries **both** the chain head and the prune watermark. **The claims made here are exactly the module docstring's two lists, and every line of both, including the "not detected" ones, has a test.** Detected without any anchor: in-place edits, interior deletions, reordering, and any row carrying no chain hashes (a direct `INSERT` with NULL hashes trips no trigger and leaves the chain around it valid, so `verify_chain` returns `ok=False` with the count in `legacy` rather than "chain intact" - `test_a_fabricated_unchained_row_is_not_reported_as_intact`, fixed in the commons `scan_chain_rows` so every adopter gets it). The witness also **travels with the export**: line 1 of an export is the anchor header, and `import_jsonl()` checks the arriving records against it at both ends, so an export shortened at its tail (`test_restore_refuses_an_export_whose_newest_records_were_dropped`) or at the oldest end of a window, which the restore would otherwise adopt as a later retention watermark (`test_restore_refuses_a_window_whose_oldest_records_were_dropped`), is refused rather than restored as "chain intact"; a trail restored from a pre-anchor export is reported unanchored until an operator re-anchors it (`test_a_pre_anchor_export_restores_but_is_never_reported_intact`). **Honest limits, asserted rather than merely admitted:** with no anchor configured, neither a tail truncation nor a forged prune is detectable (`test_without_an_anchor_a_truncated_tail_is_honestly_undetected`, `test_without_an_anchor_a_forged_prune_is_honestly_undetected`); an actor holding BOTH the store and the anchor can recompute everything, because the chain carries no secret, and that includes clearing any of the above by calling `reanchor()`, which re-witnesses the present and asserts nothing about the past; the trail proves that content changed, not who changed it; and the optional Firestore-emulator branch is unchained, so verify/export/restore refuse to run against it (`test_the_unchained_emulator_branch_refuses_to_claim_verification`). The windowed-buffer deviation is therefore **bounded, not resolved**: pruning is verifiable only to the extent that an external anchor is separately held. `agent-observability audit verify / export / restore` is the operator surface (`tests/test_cli_audit_commands.py`), and `scripts/portability_demo.py` exports, restores and re-verifies the chain in CI. **Not proven offline:** live retention behaviour, log-based alerting and regulator read-back against the managed bucket in a named GCP project. |

## Gaps carried to systems/

Hrz5's mandated `docs/runbook.md` and `docs/onprem-migration.md` are both present, so those
`Capability gaps` on the maintainer's per-system register do not apply (UI and ADK agent remain
`n/a` by design as a control-plane service). The remaining
quality-of-adoption gaps this audit surfaces, none load-bearing, are:

- **D5 live enforcement evidence (the only remaining gap).** The posture is fully expressed as code
  and gated offline (Org Policy residency allowlist and require-CMEK, per-service CMEK bindings with a
  rotation variable, dry-run-first VPC-SC perimeter, posture alerts, plus app-load residency validation),
  but nothing here proves it is *in force*. That requires a named production GCP project: an Org Policy
  evaluation showing an out-of-region create denied, a resource reporting the CMEK key in use, and a
  quiet dry-run VPC-SC window before promotion. None of it can be produced offline, so D5 stays PARTIAL
  and its remaining half is a deployment task, not a code task.

There is also one standing infrastructure blocker unrelated to this repository's code: the GitHub
hosted CI did not exist until GitHub Actions became the fleet's gate on 2026-09-02 and every CI-execution claim in this
projection is evidenced by running the same commands locally instead.
